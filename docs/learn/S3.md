# S3 — Index and search: BM25, embeddings, RRF and reranking

Box 4 and 5 on the map in [`00-overview.md`](00-overview.md): store every chunk twice, then find the right ones.

## 1. What this is, in plain English

After parsing and chunking, the corpus is a pile of **chunks**: passages of a few paragraphs each, with the IDs of the paragraphs they cover. Search is the job of picking the handful of chunks that bear on a question. We do it four ways, because each one is good at something different and bad at something else.

- **BM25** is *keyword* search. It scores a chunk by how many of the query's words it contains, counting rare words (*"Soering"*) for much more than common ones (*"the"*), and mildly preferring shorter chunks. It's the same family of maths as classic search engines. It has no idea what words *mean*: "deport" and "expel" are strangers to it. We use the `pg_search` extension, which gives Postgres a BM25 index (`paradedb.score(...)` returns the score).
- **Vector search** is *meaning* search. An **embedding model** (here `BAAI/bge-small-en-v1.5`, running locally and free) turns a text into a list of 384 numbers, a **vector**, so that texts with similar meaning land near each other. We embed every chunk once at ingest, then embed the query and ask Postgres (`pgvector`, with an HNSW index, a fast approximate nearest-neighbour structure) for the nearest chunks by **cosine similarity** (the angle between two vectors: 1 = same direction).
- **Hybrid** runs both and merges the two ranked lists with **Reciprocal Rank Fusion (RRF)**. Every chunk gets `1 / (60 + rank)` from each list it appears in, and the scores are added. A chunk that is high in *both* lists wins; no score needs normalising, because only the *ranks* matter. 60 is the standard damping constant.
- **Reranking** takes the top 30 fused chunks and has a **cross-encoder** (`BAAI/bge-reranker-base`) read the query and each chunk *together*, then give a relevance score. This is slower and smarter than the two retrievers above, which compare a query and a chunk only through numbers computed separately. So it only looks at a short list.

On top of that, every search can be narrowed by **metadata filters**: article, document type, outcome, dates. They are applied *inside* the BM25 and vector queries, not afterwards. (If you took the top 50 and *then* filtered, a narrow filter could leave you with nothing even though matching chunks exist.)

## 2. Why it matters for answer quality

The answer step can only cite what search hands it. Take the demo question *"Does the Convention stop the UK deporting criminals?"*, or just a name:

- Searching `Soering` with BM25 puts *Soering v UK* first, because the name is a rare word. Vector search also finds the case, but with weaker similarity (about 0.63, against about 0.78 for a real topical match): a bare name carries little meaning for the embedder.
- Searching *"extradition to face death row"*: BM25 returns ten chunks of Soering, because those chunks contain the words. Vector search returns Soering first, then other related cases (*Harkins and Edwards*, *Babar Ahmad*). It matches the *topic*, not the exact words, so its list is more varied. Which is "better" depends on what the answer needs.
- For a long, chatty question, each retriever alone returns a different, partly off-topic top 5. Hybrid rewards chunks both agree on, and the reranker reads the actual text against the question to push the best to the top.

Whatever the answer step is shown, it cites. Good retrieval here is the difference between a balanced, cited answer and a confident one built on the wrong paragraphs. That is why the Lab page shows each method's score and rank per hit: you can see which step helped.

## 3. How it works here

```
infra/migrations/0001_schema.sql    tables + BM25 index + HNSW index
py/rag/index/
  db.py        connect / migrate (idempotent, schema_migrations) / reset
  embedder.py  get_embedder(): bge-small (384-d, L2-normalised, CPU, batch 32) or "fake"
  store.py     upsert_document, replace_chunks, stored_hashes, record_ingest_run
  cost.py      price_usd, log_cost  (config/model-prices.json; local models cost $0)
py/rag/search/
  retrieval.py bm25_search, vector_search  (join documents, filters inside the query)
  fusion.py    rrf()
  rerank.py    get_reranker(): bge-reranker-base or "fake"
  core.py      search(conn, request) -> SearchResult
  __main__.py  the CLI behind `pnpm search`
```

```
              query
         ┌──────┴──────┐
     BM25 top 50    embed query → vector top 50      (filters applied inside both)
         └──────┬──────┘
          RRF (k=60)          bm25-only / vector-only modes stop before here
                │
      top 30 → cross-encoder  (hybrid_rerank only)
                │
          at most 50 hits, each with bm25/vector/rrf/rerank score + rank (null if not run)
```

Details worth knowing:

- Query text is turned into plain lowercase words joined with `OR` (stop-words like "the" dropped), so punctuation or words like `AND` in a question can't be read as search syntax.
- The BGE embedder wants a short instruction prefix on **queries** (not on passages). `Embedder.embed_query` adds it.
- `hybrid_rerank` reranks the top 30 fused chunks. If you ask for more than 30, the rest follow in fused order with null rerank fields. If `RERANK_ENABLED=0` and no reranker is passed in, it behaves like `hybrid` rather than loading the model.
- `paragraph_ids` on a hit is every paragraph the chunk covers; they are what the answer step may cite.
- Each query embedding and each rerank is logged to `cost_log` (cost $0, but you see the volume and the time on `/stats`).
- The first call in a process loads the models (about 4 s for the embedder, 2 s for the reranker on this machine). Servers load them once at startup.

Measured on the snapshot (96 HTML cases, 5,901 `recursive` chunks), warm, p50 over 10 queries: BM25 **37 ms**, vector **18 ms**, hybrid **55 ms**, hybrid + rerank **0.97 s**.

## 4. Try it

Run from the repo root. Prerequisites: the database is up (`docker compose up -d --wait`), the snapshot is ingested into your `DATABASE_URL` (`pnpm ingest:snapshot`), and the `ml` Python group is installed (`cd py && uv sync --group ml`). The first run of a command takes a few extra seconds to load the model.

1. **Names: BM25 shines.** `pnpm search "Soering" --mode bm25 -k 5` → the top hit is *SOERING v UK* with a BM25 score and rank, and no vector columns → BM25 is excellent at exact, rare words. Now `pnpm search "Soering" --mode vector -k 5`: Soering still comes first, but the similarity scores are lower (about 0.63 instead of about 0.78 for a topical query) → the embedder has no idea what the bare name stands for; it only matches chunks that repeat it.
2. **Meaning: vector search gives a more varied list.** `pnpm search "extradition to face death row" --mode bm25 -k 10` → all ten hits are *Soering* chunks (they contain those words). Then `--mode vector -k 10` → Soering is first, but *Harkins and Edwards* and *Babar Ahmad* appear among the others → vector search matches the topic, not the words, so it brings in related cases that don't share the exact vocabulary. Also try the paraphrase `"is it cruel to keep a condemned prisoner waiting for execution"` in both modes: BM25 finds Soering chunks first, vector puts *Vinter* and *Babar Ahmad* first and Soering third, so neither is simply "right"; this is why we fuse them.
3. **Fusion.** `pnpm search "Does the Convention stop the UK deporting criminals?" --mode hybrid -k 5` → the table shows `bm25 …#n`, `vec …#n` and `rrf …#n` per hit. A `-` in a column means that retriever didn't have the chunk in its top 50. Check the arithmetic: a hit at bm25 rank 9 and vector rank 25 has RRF = 1/69 + 1/85 ≈ 0.0263 → rank agreement beats being first in only one list.
4. **Reranking, same query.** Repeat step 3 with `--mode bm25`, `--mode vector`, `--mode hybrid` and `--mode hybrid_rerank` and compare the five case names and snippets. The reranked list adds a `rerank` column (0 to 1) and often puts different chunks first → a cross-encoder reading query and text together re-orders what the cheaper methods found. Judge for yourself whether the new order is better; that is exactly what the eval (S6) measures.
5. **Filters.** `pnpm search "deporting a criminal who has family in the UK" --mode hybrid -k 10 --article 8 --doc-type judgment --outcome no_violation` → every hit comes from an Article 8 judgment with outcome `no_violation` (i.e. cases where deportation was allowed). Try `--doc-type decision --outcome inadmissible` and `--date-from 2010-01-01` → the set changes but is still full, because filtering happens inside the search, not after it.
6. **Chunking.** `pnpm search "death row phenomenon" --mode vector --chunking fixed -k 3`, then the same with `--chunking by_section` → the hits differ: `fixed` chunks are about 256-token windows that ignore paragraph boundaries, `by_section` chunks can be up to about 480 tokens and may span several paragraphs (the paragraphs column shows `§first..last(count)` once there are more than three). Longer chunks carry more context but are blunter to cite → chunking changes what search can find; S6's eval compares the three.
7. **Raw JSON, the exact shape the Lab page receives.** `pnpm search "Soering" --mode hybrid -k 2 --json` → every `scores` field is present, `null` when that method didn't run, plus `timings_ms`.

## 5. Limits / what can go wrong

- **BM25 doesn't understand synonyms or inflections.** "Deport" won't match "deportation" (there is no stemming). The vector side and the reranker compensate; that is the point of hybrid.
- **Vector search is approximate and fuzzy.** The HNSW index can miss the true nearest neighbour; with filters it is made to keep searching until it has 50 passing rows, but results are still "similar", not "relevant". A short query can match boilerplate (e.g. the legal summaries' headers).
- **Scores aren't comparable across methods.** BM25 scores are unbounded and depend on the query; cosine sits around 0.7 to 0.8 for decent matches with this model; RRF scores are tiny by design (about 0.016 to 0.033); rerank scores are 0 to 1 and saturate: several top chunks can show 0.9999. Only ranks within one column are meaningful.
- **RRF can surface chunks neither list ranked first** (a chunk at rank 9 and 25 can beat one that was first in just one list). That is a feature when it works and noise when both lists are weak.
- **The reranker only sees the top 30** (and truncates long chunks at 512 tokens). If the right chunk isn't in the fused top 30, it can't be rescued. It also costs about a second per query on CPU.
- **A cross-encoder can be confidently wrong,** for example preferring a topically similar passage to the one that actually answers the question. Don't read its order as ground truth.
- **A paragraph can sit in several chunks** (fixed chunks overlap), so a result list can contain near-duplicates.
- **Models come from the Hugging Face cache.** If `bge-small` or `bge-reranker-base` isn't cached, the first run downloads them (about 130 MB and 1 GB). Set `HF_HOME` to reuse an existing cache.
- **Changing the embedding model means re-embedding everything,** and the vector column is fixed at 384 dimensions.
