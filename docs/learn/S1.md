# S1 — Ingest: getting documents into the database

Code: `py/rag/ingest/` · Run it: `pnpm ingest:snapshot`, `pnpm ingest:full`

## 1. What this is, in plain English

**Ingest** is the first stage of the pipeline: it takes documents from outside (court judgments, the Convention, the Human Rights Act) and walks every one of them through the later stages until they are searchable rows in the database:

```
file on disk → parse → chunk (×3 strategies) → embed → index (database)
```

- **Parse** turns a messy HTML file into numbered paragraphs (`001-57619§88`). That is S2's job; ingest just calls it.
- **Chunk** groups paragraphs into search-sized pieces. We do it three ways (`fixed`, `recursive`, `by_section`) so the lab page can compare them.
- **Embed** turns each chunk into a list of 384 numbers (a *vector*) whose position encodes its meaning. We use a small local model, `BAAI/bge-small-en-v1.5`, on the CPU. We send it 32 chunks at a time (*batch size 32*) because that keeps the CPU busy without running out of memory.
- **Index** stores everything in Postgres so BM25 (word search) and vector search can find it. That is S3's job.

Two properties make ingest safe to run again and again:

- **Incremental.** Each stored file has a **content hash**: its *sha256*, a 64-character fingerprint of the file's bytes. Change one byte and the fingerprint changes completely. Ingest compares the fingerprint of every file with the one stored in the database. If they match, the document is skipped. If not, it is re-processed. New documents just add to what is there, and nothing is ever processed twice.
- **Resumable.** In full mode the download takes over an hour. If it stops (laptop sleeps, HUDOC shows a check), the listing and the files already downloaded stay on disk and the next run carries on where it left off.

Every run writes an **`IngestRun`** row: when it started and finished, how many documents were new / changed / skipped / failed, and how many seconds each stage took. The `/stats` page shows the latest one.

## 2. Why it matters for answer quality

Retrieval can only find what was ingested, and exactly as it was ingested. If a document is silently missing, the system will answer "I can't find that" about a case it should know. If an old version lingers after HUDOC corrects a judgment, the answer would cite wording that no longer exists. If one broken document aborted the whole run, you would find out weeks later that half the corpus never loaded.

A concrete example from this corpus: *Soering v UK* (`001-57619`) is the case behind every "can the UK extradite someone who faces the death penalty?" answer. If its download had been cut off half-way and nobody noticed, the paragraph with the key sentence (§111) would be absent, and the answer would be confidently wrong. That is why ingest **verifies every file's sha256 against the manifest before using it**, records failures instead of hiding them, and counts everything in the `IngestRun`.

## 3. How it works here

```
py/rag/ingest/
  __init__.py   run_ingest(conn, source, limit=, reset=)  → IngestRun dict
  __main__.py   the CLI (python -m rag.ingest …), stops cleanly on HUDOC blocks
  pipeline.py   per-document: read+verify → skip? → parse → chunk×3 → embed → index
  snapshot.py   reads data/snapshot/manifest.json
  full.py       lists HUDOC, downloads bodies to data/full/, writes data/full/manifest.json
  hudoc.py      the HUDOC client (through Orca's browser), challenge detection, row → ManifestEntry
  ratelimit.py  ≤ 1 request/s across processes, plus a hard cap
  progress.py   per-document line with ETA, and the summary table
```

**Snapshot mode** (offline, the demo default) reads the 98 documents that are committed in `data/snapshot/`. "Download" in the `IngestRun` is just reading those files and checking their hashes.

**Full mode** has two steps:

1. `FullDownloader` asks HUDOC for the listing (the five UK English document families from `docs/hudoc-measurement.md`, 500 per page), downloads each HTML body to `data/full/hudoc/<itemid>.html` and writes `data/full/manifest.json` in the same shape as the snapshot's. The Human Rights Act comes from legislation.gov.uk with plain `httpx`.
2. The same pipeline as snapshot mode processes that manifest.

**The ETA** on each progress line is simple arithmetic: *time elapsed so far ÷ documents finished × documents left*. Skipped documents (nearly free) and new ones (slow, embedding) both feed the average, so a run that starts with 90 skipped documents will estimate "very quick" and then correct itself when it reaches a new one. It is an estimate, not a promise.

### Rate limiting and politeness

HUDOC is a public service run by the Court. We promised to ask for **at most one thing per second**, and the promise is enforced in code, not by good intentions:

- `RateLimiter` takes a *file lock* shared by every process on the machine (two ingest runs cannot add up to 2 requests/second), reads the time of the previous request, sleeps until 1.05 s have passed, then writes its own timestamp.
- A **hard cap** (`HUDOC_HARD_CAP`, default 6000 requests in total) and a per-run cap (`--max-requests N`) stop everything if something loops.
- Every request is appended to `data/full/hudoc-requests.jsonl` (time, URL, status, bytes, duration) so you can audit the real rate afterwards.
- After 5 failed downloads in a row, the run stops instead of hammering a server that is unhappy.

### Why HUDOC needs a browser tab

HUDOC sits behind a **Cloudflare managed challenge**: a gate that decides if the visitor is a real browser. A plain HTTP client (Python `httpx`, `curl`) gets `403 Forbidden` and a page titled "Just a moment…". A real browser passes the gate once, and then its requests are accepted.

So full mode sends its requests as **same-origin `fetch()` calls inside Orca's built-in browser tab** (`orca eval`). "Same-origin" means the JavaScript runs on `hudoc.echr.coe.int` itself and asks the same site, so the tab's cookies come along automatically. Our Python code only decides *what* to fetch and *when*.

We never try to solve or sneak past the challenge. If any answer looks like one (a 403/429, the Cloudflare header, or the challenge page), the run **stops**, keeps everything downloaded so far, and tells a human what to do: open the HUDOC tab in Orca, complete any check, run the command again.

### Resumability

| What | Where | How it resumes |
|---|---|---|
| Listing | `data/full/listing.json` | Cached page by page; reused for 24 h |
| Downloaded bodies | `data/full/hudoc/*.html` | Written to a `.part` file then renamed, so there are no half-files; existing files are never fetched again |
| Request counter | `data/full/hudoc-state.json` | Lifetime count and last request time, shared across processes |
| Last stop reason | `data/full/state.json` | `ok` or `blocked` with the reason |
| Database | Postgres | Each document is committed on its own; a re-run skips it by hash |

## 4. Try it

All commands from the repo root.

1. **Incremental hashing.** Run `pnpm ingest:snapshot --reset`, then run `pnpm ingest:snapshot` again.
   → The second run prints `skipped` on every line and finishes in about 5 seconds in total (0.04 s of actual work; the rest is starting Python), with `docs: unchanged_skipped = 98`, `new = 0`.
   → This proves unchanged documents are recognised by their content hash and never re-embedded.
2. **One byte changes everything.** Edit one character in a stored snapshot file and run `pnpm ingest:snapshot`. (`git checkout data/snapshot` afterwards to undo.)
   → The document shows as `FAILED … sha256 mismatch`, the other 97 are skipped, and the run still completes.
   → This proves integrity is checked before anything is used, and that one bad document does not abort the run.
3. **Start from empty.** Run `pnpm ingest:snapshot --reset`.
   → Everything is `new`; the summary table shows seconds per stage (download, parse, chunk, embed, index). Embed dominates (about 210 of 211 seconds of wall clock on the reference run below).
   → Compare with `docs/learn/ingestion-estimates.md`: embedding the three strategies on the CPU is where the time goes.
4. **A small slice.** Run `pnpm ingest:snapshot --limit 5` (add `--reset` to start clean).
   → Only five documents are processed, and `seen = 5`.
   → Useful when you are experimenting and don't want to wait.
5. **Look at the run.** After any run, `psql` (or the `/stats` page later) shows the stored `IngestRun`:
   `docker compose exec -T db psql -U echr -d echr -c "select payload->'counts', payload->'stage_seconds' from ingest_runs order by started_at desc limit 1"`
   → counts and per-stage seconds match what the summary table printed.
6. **Politeness, audited** (needs the Orca browser tab; makes 7 HUDOC requests: 1 listing, 5 documents, 1 count of the skipped Commission reports): `pnpm ingest:full --limit 5`, then
   `python3 -c "import json;r=[json.loads(l) for l in open('data/full/hudoc-requests.jsonl')];print([round(b['t']-a['t'],2) for a,b in zip(r,r[1:])])"`
   → Every gap is ≥ 1.05 seconds.
   → This proves the one-request-per-second rule is enforced by the code, not by luck.

### Real timings (snapshot, from empty, `pnpm ingest:snapshot --reset`)

Measured on the Apple M4 Pro with bge-small on the CPU, while other agents were also using the machine (load average about 9 on 14 cores), so an idle machine should be a little faster. Seconds spent in each stage, next to what `docs/learn/ingestion-estimates.md` predicted (G0b's prototype chunkers; "download" is 103 s of waiting on HUDOC there and about 0 s here, because the files are already on disk):

| Stage | Measured (this pipeline) | Estimate (G0b, 3 strategies) | Why different |
|---|---:|---:|---|
| download (file reads + sha256) | 0.03 s | 103 s (HUDOC) | snapshot is local |
| parse | 0.72 s | 0.40 s | real parser handles all 98 documents, incl. legislation |
| chunk | 10.8 s | 6.1 s | real tokenizer counts tokens; more chunks |
| embed | 209.9 s | 147.4 s | S2's chunkers make 22.7 k chunks, G0b's made 13.7 k; machine was busy |
| index | 18.6 s | 3.6 s | rows are written document by document into live BM25 + HNSW indexes, not bulk-loaded then indexed |
| **Wall clock** | **211 s** (215 s with Python start-up and model load) | 46 s + 103 s download | |

Stage seconds add up to 240 s but the wall clock is 211 s, because **embedding runs in a worker thread**: while document N is being embedded, the main thread writes document N-1 to the database and parses and chunks document N+1. Overlapping saved roughly 25 s (237 s → 211 s in back-to-back runs). Chunks are also batched longest-with-longest (32 at a time) so short chunks don't get padded up to the length of a long one.

## 5. Limits / what can go wrong

- **Full mode needs a human sometimes.** If Cloudflare shows its check, the run stops (exit code 2) with instructions. Complete the check in Orca's HUDOC tab and re-run: nothing is lost.
- **One browser hiccup does not stop a run, but a block always does.** If `orca` itself fails (exits non-zero, times out, or prints something unreadable) the request is retried up to 3 times, after waiting 5 s, 15 s and 45 s. Before each retry the HUDOC tab is looked up again (its page id may have changed) and recreated if it is gone. Every retry goes through the same limiter (still at most 1 request per second) and gets its own row in `data/full/hudoc-requests.jsonl` (`status` -1 for the failures, plus a `retry` number: 0 for the first try), and one line is printed: `[retry 1/3] orca eval failed (…); waiting 5 s`. After the 3rd retry fails, the run stops as before with `STOPPED: cannot reach HUDOC through Orca's browser`. **Never retried:** a 403, 429 or 503, a Cloudflare challenge, or a search answer that is not JSON. That is a block, and the run stops at once so a human can look. Also not retried: `orca` missing from PATH, or no tab that can be created.
- **A re-run does not re-download files already on disk**, even if HUDOC corrected the text. To pick up a correction, delete that file from `data/full/hudoc/` and re-run; the new hash then triggers re-processing.
- **Removed documents stay.** If HUDOC withdraws a document, ingest does not delete it from the database. `--reset` starts from empty.
- **HUDOC lists some documents twice.** In the one real full run, HUDOC said it had 2,532 decisions but only 2,522 were distinct (10 repeats). The listing pager therefore moves by HUDOC's own position (`next_start`, advanced by the rows each answer *contained*, not by how many were new), and stops when an answer is empty, when the position reaches HUDOC's count, or when two answers in a row bring nothing new. It then prints `[listing decisions] WARNING: 2522 unique of 2532 listed (10 duplicates)` and treats the listing as complete. A hard cap of `ceil(count / 500) + 3` listing requests per query turns any other paging surprise into a clear error instead of a loop. An earlier version paged by the unique count and re-asked for the same page about 700 times.
- **Commission reports are skipped.** The contract's document types have no value for them, so full mode neither downloads nor parses them. It asks HUDOC once how many there are (a count-only request, cached for 24 h) and prints `skipped_commission_reports=<n>` in the summary and the log (307 on 2026-11-03). The number is deliberately *not* part of `IngestRun` (a strict contract object), so it is not counted in `seen` and does not appear on `/stats`.
- **The Convention in full mode** reuses the already-cleaned text from the snapshot, because turning the Court's PDF into clean text needs a PDF library that is not a project dependency.
- **In full mode the download and the embedding run one after the other** (all downloads, then all parsing and embedding), so a full run takes roughly the download time plus the embedding time (see `docs/learn/ingestion-estimates.md`). Only the embedding is overlapped with parsing and database writes.
- **A half-written document is removed again.** If storing a document fails part-way, ingest deletes its row, so its hash cannot make the next run skip a document that has no chunks.
- **`pnpm search …` is not our search.** pnpm has a built-in `search` command (it searches the npm registry). Use `pnpm run search "Soering" --mode bm25`.
- **The ETA is a mean**, so it is rough while few documents are done and when the mix of document sizes is uneven.
- **Politeness is only as good as the single machine**: the limiter coordinates processes on this computer, not other computers.
