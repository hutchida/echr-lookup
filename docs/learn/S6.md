# S6: How we measure whether the answers are any good

## 1. What this is, in plain English

A RAG system (retrieval-augmented generation: find relevant passages, then have a language model write an answer from them) can go wrong in two separate places. The **retrieval** step can fail to find the passage that holds the answer. Or the **generation** step can have the right passages and still write something they don't support. Without measurement you only find out by reading answers and having a feeling.

The eval is a fixed set of questions with a known "right place to look", plus a runner that asks the system each question and scores it. Because the questions never change between runs, a number going up or down means the *system* changed. That is how we choose between chunking strategies (how judgments are cut into searchable pieces), search modes (BM25 keyword search, vector search, the two fused, fused then reranked) and whether the reranker earns its seconds.

There are 71 questions in `data/eval/questions.jsonl`: 48 `explain` questions (a legal point with expected paragraphs), 12 `stat` questions (a count answered by SQL over metadata, with the right number known), and 11 `neutrality` questions (contested topics, where the test is balance, not accuracy). **All are `draft`**: I wrote them and chose the expected paragraphs, Dan reviews them.

## 2. Why it matters for answer quality

Take the question *"Can the UK extradite a person who faces the death row phenomenon?"* Its expected paragraphs are `001-57619§91` (the Soering rule: extradition can breach Article 3 if there is a real risk of ill-treatment abroad) and `001-57619§111` (the key sentence applying it to death row).

Suppose search returns ten hits and the first one containing §111 is at position 7, with §91 nowhere in the top 10:

- **Recall@5** = 0 of 2 expected paragraphs in the top 5 → **0.0**.
- **Recall@10** = 1 of 2 in the top 10 → **0.5**.
- **MRR** (mean reciprocal rank) for this question = 1 / 7 ≈ **0.14**. Averaged over all questions, 1.0 would mean the evidence is always the first hit.

A system with these numbers might still write a decent answer from §111 alone, but it would be missing the general rule and would often fail on harder questions. That is exactly what the table lets us see and fix.

Then the answer is judged. **Faithfulness**: an LLM judge reads each claim and the paragraphs it cites, and scores 1 (fully supported), 0.5 (partly), 0 (not). "Extradition can breach Article 3 where there is a real risk of ill-treatment (`001-57619§91`)" scores 1. The same sentence citing `001-57619§88` (the absolute-prohibition paragraph) would score 0.5 at best: true law, wrong support. **Citation accuracy** asks the narrower question per citation: does *this* paragraph support *this* claim?

## 3. How it works here

```
data/eval/questions.jsonl ──► items.py   load + validate against the EvalItem contract
                                 │
        for each chunking x mode (3 x 4 = 12 configs):
                                 ▼
                  runner.py: rag.search(query, mode, chunking, k=10)
                                 │   metrics.py: recall@5, recall@10, MRR   ($0, local)
        default config (recursive + hybrid_rerank) and a comparison config (recursive + hybrid):
                                 ▼
                  rag.answer.answer(question) ──► judge.py (Sonnet via rag.answer.llm.complete,
                                 │                  purpose "judge"): faithfulness, citation accuracy,
                                 │                  neutrality; stat questions: count == expected?
                                 ▼
          eval_runs table (one EvalRun per config) ─► report.py ─► docs/eval-results.md + README
```

Files in `py/rag/eval/`:

- `metrics.py`: recall@k, MRR, mean, stat check. Pure functions, tested with hand-worked examples.
- `judge.py`: the rubrics and the code that turns the judge's JSON into scores. Per-claim verdicts are averaged **in code**; the model never states a total.
- `runner.py`: `run_config` (one config), `run_eval` (all of them), the cost guard, `store_run`. It talks to the rest of the system only through a `Backend` object, so tests use fakes.
- `report.py`: the markdown table, the "what this shows" paragraph (built from the numbers), README replacement between `<!-- eval:start -->` and `<!-- eval:end -->`.
- `cli.py`: `python -m rag.eval --source snapshot [--quick] [--no-judge] [--max-cost 3.00]`, which is `pnpm eval:snapshot`.

Choices worth knowing:

- A hit "counts" if **any** of its `paragraph_ids` is expected. Recall is the share of expected paragraphs covered by the top-k hits' `paragraph_ids`; MRR uses the first relevant hit.
- **Citation accuracy is judged independently by Sonnet**, not reused from S4's own verification status (Haiku), so the pipeline doesn't mark its own homework.
- **Cost guard**: before any paid call the runner prints an estimate and aborts above `--max-cost`. It also stops answering if actual spend reaches the limit. The comparison config only answers an even sample of 25 questions to keep the full run under $3.
- `--quick` = 10 questions, retrieval only, nothing stored or written. `--no-judge` skips answer generation and judging for explain and neutrality questions but still answers the cheap counting questions.

## Results on the snapshot (first full run, 2026-11-03)

Retrieval, 59 explain/neutrality questions with expected paragraphs (answer-level rows ★ below):

| Chunking | Mode | Recall@5 | Recall@10 | MRR | Case hit@10 |
|---|---|---|---|---|---|
| fixed | bm25 / vector / hybrid / hybrid_rerank | 0.19 / 0.19 / 0.18 / 0.21 | 0.29 / 0.27 / 0.31 / 0.32 | 0.18 / 0.24 / 0.19 / 0.19 | 0.88 (all four) |
| recursive | bm25 / vector / hybrid / hybrid_rerank | 0.21 / 0.18 / 0.19 / 0.17 | 0.24 / 0.22 / 0.25 / 0.28 | 0.16 / 0.21 / 0.23 / 0.16 | 0.83 / 0.83 / 0.86 / 0.90 |
| by_section | bm25 / vector / hybrid / hybrid_rerank | 0.22 / 0.22 / 0.23 / 0.19 | 0.31 / 0.30 / 0.32 / 0.32 | 0.22 / 0.22 / 0.24 / 0.18 | 0.85 / 0.88 / 0.90 / 0.92 |

Answer level: recursive + hybrid_rerank (default, 71 questions): faithfulness 0.96, citation accuracy 0.98, neutrality 0.55, stat accuracy 0.50 (first run; 0.92 to 1.00 after S4-fix), cost $1.57. Recursive + hybrid (25-question sample): 0.96 / 0.94 / 0.75 / 0.50, $0.55. Full table, timings and notes: `docs/eval-results.md`. Whole run: 8 min 19 s, $2.12.

How to read this, in order of importance:

- **Search finds the right case about 87% of the time (Case hit@10) but the exact expected paragraph only about 29% of the time (recall@10).** The expected paragraph's neighbours are often retrieved instead; strict paragraph-level labels count those as misses. For citing, the neighbours are frequently fine, so the recall numbers understate real usefulness; they are still the right yardstick for *comparing* configs.
- **Hybrid is the safest search mode**: it matches or beats BM25 and vector on recall@10 for all 3 chunkings and on MRR for 2 of 3 (fixed chunking: vector alone wins on MRR, 0.24 vs 0.19).
- **The reranker did not pay for itself on first-hit quality**: it nudges recall@10 up for fixed and recursive chunks but lowers MRR on average (about -0.04) and costs 55-125 s per config instead of 2-3 s. Differences this small on 59 questions are close to noise.
- **Chunking matters less than search mode**; by_section is marginally best on average MRR (0.21 vs 0.20 and 0.19).
- **Answers are faithful when they exist** (0.96) and citations are accurate (0.94-0.98): the system rarely claims something its cited paragraph doesn't say.
- **Neutrality is the weak spot** (0.55 and 0.75, i.e. 6 of 11 and 3 of 4 answers passed the "balanced and no opinion" rubric). The runner does not store the judge's reason, so a first thing to try is reading those answers yourself.
- **Counting questions: 6 of 12 exact** (as first measured; S4-fix, #13, later took this to 11/12, see `docs/eval-results.md`). The misses: "declared inadmissible" returned 35 (includes the 2 partly-inadmissible decisions; I expected 33); "at least one violation" returned 16 (violation only, not "mixed"; I expected 24); "Grand Chamber judgments" returned 41 (no chamber filter was applied); the deportation-complaint counts came out one to three higher than the README list (30 vs 27, 6 vs 5). Some are different readings of my questions, some look like real SQL gaps in the stats route. Those are for you and S4's owner to judge.

## 4. Try it

1. **Check the question set is sound.** Run `cd py && uv run pytest rag/eval -q` → 24 tests pass, including "every expected paragraph id exists in the snapshot" and "every stat count matches the manifest" → proves the questions point at real text and the counts aren't made up.
2. **Look at what a question expects.** Run `head -1 data/eval/questions.jsonl | python3 -m json.tool` → the Soering question with `expected_paragraph_ids` §91 and §111 and `"status": "draft"` → shows the unit of evidence is a paragraph id, and that nothing is "reviewed" until you say so.
3. **Spot-check an expected paragraph.** Pick any id, e.g. `001-70442§82` (Hirst), and search the stored HTML: `grep -o "blunt instrument" data/snapshot/hudoc/001-70442.html | head -1` → one hit → confirms the paragraph really contains the point the question asks about. Disagree with one? Edit the line and tell me.
4. **A fast smoke test (after S1–S4 are merged and ingested).** Run `pnpm eval:snapshot --quick` → a 12-row table over 10 questions, in seconds, nothing written → proves the plumbing works at no cost.
5. **Retrieval only, all 12 configs.** Run `pnpm eval:snapshot --retrieval-only` (about 4.5 min, $0; it rewrites `docs/eval-results.md`) → table with Recall@5/10, MRR and Case hit@10 per chunking × mode; compare `bm25` with `vector` → shows which kind of search finds the evidence for legal questions, and whether `hybrid_rerank` beats plain `hybrid`.
6. **The cost guard.** Run `pnpm eval:snapshot --max-cost 0.10` → prints the estimate and exits with "Aborted before any paid call" → shows spending is bounded before it starts.

## 5. Limits / what can go wrong

- **Draft questions.** Expected paragraphs are my judgement of where an answer lives. A good retrieval hit on a *different* relevant paragraph counts as a miss, so recall is a floor, not a truth. Paragraph ids in unnumbered documents (`§u1`…) aren't used because their numbering isn't stable until S2's parser defines it; decisions such as Z. and T. or Ali are therefore not represented in the explain set.
- **71 questions is a small sample.** Differences of a few hundredths between configs are noise; look for gaps of 0.1 or more.
- **An LLM judge is itself fallible and not free.** The rubric, the fixed 0 / 0.5 / 1 verdicts and temperature 0 make it consistent, not correct. Judge and generator are the same model family (Sonnet), which can flatter the answers. Spot-check a few judgements by hand.
- **Neutrality is a pass/fail rubric** (balanced *and* no opinion), so it is blunt. A refusal to engage scores as "no opinion" but would fail "balanced".
- **Stat accuracy isn't in the contract.** `EvalRun.metrics` has no field for it, and `EvalItem` has no field for the expected count, so: stat accuracy appears only in `docs/eval-results.md` and the README (not in `eval_runs`/`/eval-runs`), and each stat item's expected count is the tag `expected_count:<n>` (also written in `reference_notes`). Agreed with the orchestrator; fixing it properly is a contract change for later.
- **Stat counts depend on definitions**: "Article 8 judgments" means the HUDOC articles list contains `8` or `8-x`; "deportation complaints" is the 27 decisions listed in `data/snapshot/README.md`; grounds come from the README's prototype oracle, which is not lawyer-verified.
- **Retrieval speed**: the runner searches 12 configs × 59 questions; the reranker configs are the slow part.
