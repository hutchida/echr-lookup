# S5: the API

## 1. What this is, in plain English

The API is the one door into the system. Everything else (ingest, search, answer, eval) is Python code that reads and writes the database. The web app never touches any of it directly: it sends an HTTP request to the API and gets JSON back. HTTP (HyperText Transfer Protocol) is the request/response language browsers use; JSON is the text format for structured data (`{"query": "Soering", "k": 5}`). The service is built with FastAPI, a Python web framework, and runs under `uvicorn`, the server that listens on a port (8000 here).

An **API contract** is a written promise about the exact shape of every request and response: which fields exist, their types, and their limits (for example, `k` is a whole number from 1 to 50). Here the contract lives in `packages/contract` as zod schemas (zod is a TypeScript library for describing and checking data shapes). They are exported as **JSON Schema**, a language-neutral way to describe JSON, which Python can check too. The web app (TypeScript) and the API (Python) are written in different languages, so a shared contract is what stops them disagreeing.

The API has eight jobs: `POST /search` (find passages), `POST /ask` (a cited answer, or a SQL count), `GET /stats` (what is in the corpus and how it has been running), `GET /case/{id}` (a whole document, paragraph by paragraph), `GET /ingest-runs`, `GET /eval-runs` and `GET /eval-runs/{id}` (history), and `GET /costs` (what the model calls have cost). `GET /health` says whether the service and database are up. It adds no search or answering logic of its own: `/search` calls `rag.search.search`, `/ask` calls `rag.answer.answer`, and the rest are plain SQL reading the tables the other tasks fill.

## 2. Why it matters for answer quality

An answer system is only trustworthy if its citations survive the trip to the screen. Take the demo question "Does the Convention stop the UK deporting criminals?". The answer cites paragraphs such as `001-57619§88`. The web app turns each citation into a link to `/case/001-57619`, which has to return the *same* paragraph, with the same id, in document order, so the right one can be highlighted. If the API quietly renamed `paragraph_id` to `paragraphId`, or sent paragraphs in the wrong order, the answer would still look fine, but the click would land on the wrong text. A contract makes that kind of drift a failing test instead of a bug a user finds.

Errors are part of the contract too. If a case id does not exist, the API replies `404` with `{"error": "not_found", "detail": ..., "request_id": ...}` every time, never a stack trace and never a differently shaped message. The `request_id` is also in the `X-Request-ID` header and in the `cost_log` table, so one id lets you follow a single question through the whole system.

## 3. How it works here

```
browser / web app ──HTTP+JSON──▶ api.main (FastAPI)
                                   │  middleware: request id, Server-Timing, CORS, 500 → ApiError
                                   │  routes.py : check the body against the contract's JSON Schema
                                   ├─ POST /search ─▶ rag.search.search(conn, request)
                                   ├─ POST /ask    ─▶ rag.answer.answer(conn, request)
                                   └─ GET  *       ─▶ queries.py (SQL → contract-shaped dicts)
                                                          │
                                                       Postgres (documents, paragraphs, chunks,
                                                       ingest_runs, cost_log, eval_runs)
```

Files in `py/api/`:

- `main.py`: the app, the **lifespan** (code that runs once when the server starts and once when it stops), the middleware, CORS, and `/health` (unchanged from the scaffold). At startup it loads the embedder (the model that turns text into vectors) and the reranker (the model that re-scores the best hits), once, so no request pays that cost. The first request would otherwise take several seconds.
- `routes.py`: the endpoints. A request body is read as plain JSON and checked with `rag.contract.contract_errors("SearchRequest", body)`. There is no second, hand-written Python copy of the contract that could drift from it. A bad body gives a `422` before any search or LLM call, so a typo cannot cost money.
- `queries.py`: the SQL for `/stats`, `/case`, the run lists and `/costs`. Column names equal the contract's field names (`docs/interfaces.md` §3), so most rows turn into contract dicts with almost no renaming.
- `errors.py`: turns every failure (unknown route, wrong method, bad body, database down, tables missing, a bug) into the `ApiError` shape with a `request_id`. Unexpected errors are logged on the server but never leak details to the client.
- `openapi.py`: builds the `/docs` page. The contract's JSON Schemas become the API's schemas, and the contract **fixtures** (one example file per schema in `packages/contract/fixtures`) become the examples shown on `/docs`.
- `db.py`: one database connection per request (`psycopg_pool` is not in the lockfile, and a local connection takes a few milliseconds).

Every response carries `X-Request-ID` and `Server-Timing: app;dur=<milliseconds>`. For `/ask`, `X-Request-ID` equals `Answer.request_id`, which is the id written to `cost_log`, so the header leads you straight to that question's costs. CORS (Cross-Origin Resource Sharing, the browser rule that a page may only call servers that allow it) is open for `http://localhost:3000` and `http://localhost:3100` only.

**How validation catches drift.** Every test that gets a response calls `contract_errors(<Name>, body)` and expects `[]`. `contract_errors` checks against the JSON Schema exported from zod, so the contract files have a single source of truth. If someone adds a field to `Answer` in zod and forgets the Python side, or renames one, or returns `null` where a number is required, a test fails with a message such as `steps/1: 'model' is a required property`. The `/docs` examples are checked the same way, so the documentation cannot go stale either. There is one subtle trap that the tests caught: FastAPI silently deletes every `null` when it builds the OpenAPI document, which made the contract's own examples invalid (`rerank_score: null` disappeared). `openapi.py` puts them back, and a test guards it.

## 4. Try it

Start the database and the API (from the repo root). If you have not run `pnpm ingest:snapshot` yet, the data endpoints answer `503 database_not_ready` (see "Limits").

```
docker compose up -d --wait
pnpm dev:api          # serves http://localhost:8000
```

1. **Browse the API as the presenter would.** Open `http://localhost:8000/docs` → a page listing every endpoint with a one-line summary. Open `POST /ask`, click "Try it out", and use the example dropdown: you see the fixture request plus the three demo questions → this shows the documentation is generated from the contract, not written by hand. Scroll to "Schemas" at the bottom: the same names as `packages/contract/src`.

2. **Look at the headers.** Run `curl -i http://localhost:8000/health` → a `200` with `x-request-id: req-…` and `server-timing: app;dur=…` → every response is traceable and timed. Run it twice and the id changes. Now send your own: `curl -i -H "X-Request-ID: my-test-1" http://localhost:8000/health` → the response echoes `my-test-1`, so a web app can tag a request and find it in the logs.

3. **See the error contract.** Run `curl -i http://localhost:8000/case/001-99999` → `404` with body `{"error":"not_found","detail":"No document with item_id '001-99999' in the loaded corpus (GET /stats shows what is loaded).","request_id":"req-…"}` and the same id in `x-request-id` → even failures have a fixed shape. Then make a request that breaks the contract: `curl -i -X POST localhost:8000/search -H 'content-type: application/json' -d '{"query":"x","mode":"fuzzy","chunking":"fixed","k":99}'` → `422`, with `detail` naming the bad fields (`mode`, `k`) → bad input is rejected before it reaches search or costs a cent.

4. **Whole case, in order (after `pnpm ingest:snapshot`).** Run `curl -s localhost:8000/case/001-57619 | python3 -m json.tool | head -40` → the Soering v UK document, then paragraphs with ids like `001-57619§88` in reading order → this is exactly what a citation link opens. Compare with `curl -s localhost:8000/case/001-57619 | python3 -c "import json,sys; print([p['id'] for p in json.load(sys.stdin)['paragraphs']][:5])"`.

5. **Search by name versus by meaning.** Run `curl -s -X POST localhost:8000/search -H 'content-type: application/json' -d '{"query":"Soering","mode":"bm25","chunking":"recursive","k":3}' | python3 -m json.tool` → Soering v UK is first, with a `bm25_score` and `vector_score: null` → BM25 (keyword ranking) matches exact names. Change `"Soering"` to `"extradition to face death row"` and `"mode"` to `"vector"` → the same case appears without the word "Soering", with a `vector_score` and `bm25_score: null` → vector search matches meaning.

6. **Corpus and money at a glance.** Run `curl -s localhost:8000/stats | python3 -m json.tool | head -60` → document and paragraph totals, counts by article, outcome, chamber and year, the last ingest run with timings, and `costs` → this is the data behind the `/stats` page. Then `curl -s localhost:8000/costs | python3 -m json.tool` → `total_usd` is `0.0` while only local models have run, and grows with each `/ask` in live mode (check it before and after one question). The `Server-Timing` header on `/stats` should read about 20 ms (budget: 500 ms).

## 5. Limits / what can go wrong

- **No pool.** Each request opens its own database connection. That is simple and fast enough locally, but under heavy load a pool would be better (it needs a new dependency, `psycopg_pool`).
- **Responses are not checked at runtime.** The tests validate them against the contract; production does not (that would cost time on every request). If the data in the database is shaped wrongly, say a bad `eval_runs` payload, the API passes it on. Contract drift is caught by tests and by the producers (ingest, eval) writing valid rows, not by the API.
- **The API trusts the other tasks' functions.** `/search` and `/ask` only validate input; what `search()` and `answer()` return is passed through unchecked. The integration tests (`py/api/tests/test_integration.py`) check them end to end on a small corpus, with a fake embedder and a fake LLM.
- **No data yet means 503.** If the tables do not exist, the API answers `503 database_not_ready` with a hint to run the ingest, rather than a `500`.
- **A failed `/ask` still keeps its cost rows.** The cost of any model call already made is committed even if a later step fails, so `/costs` reflects what was actually spent.
- **No authentication and no rate limiting.** It is built for local use and a demo. Do not put it on the public internet as it is: anyone who can reach `/ask` can spend your Anthropic budget.
- **Model start-up.** Loading the embedder and reranker takes seconds, so the server is slow to start, and the first `/search` after a restart waits for it. Every request after that is warm.
- **Reranking is the slow part.** Measured on the 98-document snapshot (warm, real bge-small embedder and bge-reranker-base, on a loaded laptop): `/stats` ~20 ms, `/case/001-57619` ~10 ms, `/search` bm25 or vector ~40 ms, hybrid ~50-80 ms, hybrid_rerank ~1.45 s (the first call after start-up ~2.3 s). `/ask` with a fake LLM takes ~1.5 s for an explain question (about 1.4 s of it is the cross-encoder rerank) and ~40 ms for a counting question that goes through SQL. With the live LLM, the Anthropic calls add to that; budget 15 s.
