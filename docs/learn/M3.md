# M3: can this run on a server, and where?

## 1. What this is, in plain English

So far echr-lookup only runs on Dan's laptop. To let claude.ai or ChatGPT call the search tools, the **MCP server** (the program that offers the tools) must run somewhere on the internet with a public `https://` address. M3 asks two questions: can the whole thing be packed into one **container image**, and where should that container run?

A **container image** is a frozen folder with a program plus everything it needs (Python, libraries, the two AI models). **Docker** runs images as isolated containers. **Docker Compose** starts several containers together from one file: here the database (**ParadeDB**, a Postgres that has `pgvector` for meaning-search and `pg_search` for **BM25**, the classic keyword-ranking formula), the **API** (FastAPI, the web server the web app talks to) and the **MCP server**. A **cold start** is the time from "container starts" to "first useful answer". **Scale to zero** means the host stops your program when nobody uses it and starts it again on demand.

M3 did not deploy anything. It built the image locally, measured it, and compared hosts using their public price pages and docs.

## 2. Why it matters

The measurement that changes the decision: searching the corpus is fast (the keyword search takes 0.01 s, the hybrid keyword + meaning search 0.08 s), but the **reranker** (a second model that re-reads 30 candidate paragraphs together with the question) takes ~15 CPU-seconds. For "Are prisoners entitled to vote?" the same search took 15.2 s on 1 CPU, 8.0 s on 2, 4.5 s on 4 and 2.9 s on 14. So the host needs 4+ CPUs, which rules out Netlify Functions (at most 2 vCPU and 60-second, short-lived, stateless functions) and most free tiers, while memory (about 1 GiB per process) and disk (2.8 GB image) are modest.

## 3. How it works here

```
repo root ──docker build──► echr-deploy-app image  (Python + CPU torch + both models + app code + data/snapshot)
                                   │ same image, two commands
 infra/deploy/compose.yml          ├─ api  : uvicorn api.main:app          → localhost:8003
   project "echr-deploy"           └─ mcp  : python -m echr_mcp --transport http --port 8100 → localhost:8103
                                   │
                              db: paradedb/paradedb:0.26.4-pg17            → localhost:5434
```

- `infra/deploy/Dockerfile`: four stages (`deps` → `models` → `runtime-slim` → `runtime-baked`). The last one is the default: models are inside the image, so starting takes 8 s and needs no internet.
- `infra/deploy/compose.yml`, `compose.slim.yml` (variant: models downloaded into a volume). The MCP service sets `MCP_HOST=0.0.0.0`; `py/echr_mcp/__main__.py` keeps the Host/Origin allow-list on for any non-local bind.
- `infra/deploy/load-snapshot.sh [ingest|dump]`: `ingest` rebuilds the corpus inside the image (531 s here, most of it embedding); `dump` copies a finished database with `pg_dump` (2 s).
- `infra/deploy/measure.py`: restarts the API and prints cold start, RAM and warm latency.
- `docs/hosting-options.md`: measurements, Netlify limits, three hosts with prices, the MCP auth rules of both vendors, the recommendation.

## 4. Try it

All commands run from the repo root; Docker must be running.

1. **Build the image and start the stack**
   `docker compose -f infra/deploy/compose.yml -p echr-deploy up -d --build`
   → ends with `Container echr-deploy-api-1 Started` and `echr-deploy-db-1 Healthy`; `docker images echr-deploy-app` lists one image. First build: about 2.5 min plus downloads (torch ≈ 700 MB, models 1.2 GB).
   *Proves:* one image contains the API and both models, and ParadeDB starts next to it on port 5434.
2. **Load the corpus**
   `infra/deploy/load-snapshot.sh dump` (needs the dev DB container; or `infra/deploy/load-snapshot.sh` to build it from scratch in ~9 minutes)
   → `loaded in 2 s (dump)` and `documents=98 paragraphs=9430 chunks=16154`.
   *Proves:* the compose database holds the same corpus, including the BM25 and vector indexes.
3. **Check health and search**
   `curl -s localhost:8003/health` → `{"status":"ok", ... "db":{"reachable":true,"extensions":["pg_search","vector"]} ...}`
   `curl -s -X POST localhost:8003/search -H 'content-type: application/json' -d '{"query":"Are prisoners entitled to vote?","mode":"hybrid_rerank","chunking":"recursive","k":5}'` → JSON with 5 `hits`, each with `paragraph_ids` such as `["001-70442§u63", …]`, in about 3 s on a fast machine.
   *Proves:* the container reaches the database, both extensions are present and the models run.
4. **Read the resource use**
   `docker stats --no-stream` → `echr-deploy-api-1` around 0.8–1.1 GiB, `echr-deploy-db-1` around 0.15 GiB.
   *Proves:* a host needs about 2 GiB per Python process plus the database, which is what §4 of `docs/hosting-options.md` is based on.
5. **See how CPU limits change search speed**
   `python3 infra/deploy/measure.py api` → lines such as `first /health 200 at 8.1s`, `warm /search ... median 2.9s`.
   Then repeat after `docker update --cpus 2 echr-deploy-api-1` → the median rises to about 8 s (set `OMP_NUM_THREADS` to match, or recreate the container, for a clean test).
   *Proves:* the reranker is CPU-bound, so the host's vCPU count sets the latency.
6. **Call an MCP tool**
   `python3 infra/deploy/measure.py mcp` → `tools/list ...: search_case_law, get_paragraphs, get_case, count_cases, corpus_info, check_quote`, then `first search 2.8s (8 hits)`. (Or `npx @modelcontextprotocol/inspector@latest` and connect to `http://localhost:8103/mcp`.)
   *Proves:* the same image serves MCP over streamable HTTP and the tool returns cited hits. Also try `curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8103/mcp -H 'Host: evil.example.com' -H 'content-type: application/json' -d '{}'` → `421`: the Host-header check (protection against DNS rebinding, a trick where a malicious web page makes your browser talk to a local server) is on even though the server listens on `0.0.0.0` inside the container.

Clean up when finished: `docker compose -f infra/deploy/compose.yml -p echr-deploy down` (no `-v` unless you also want to delete the database volume; only this project's).

## 5. Limits / what can go wrong

- All numbers come from one Mac (arm64, 14 CPUs in Docker's VM). A real x86 server will differ; the 1/2/4 CPU rows were produced by capping the container, not on a real small VM.
- amd64 images were built only to measure their size; they were not run.
- The stack in `compose.yml` uses throw-away credentials (`echr`/`echr`) and publishes ports to the host; a real deployment must not.
- `/ask` does not work in this stack: there is no Anthropic key and `LLM_MODE=fake`. Only search and the MCP tools are exercised.
- Prices change. They were read on 2026-11-04 and the docs say how each was derived; ChatGPT plan eligibility for custom MCP servers could not be confirmed from the vendor docs available.
- The API's CORS list and the web app's `API_URL` are not configurable for a deployed web app yet (out of this task's scope).
