## Why
Claude + tools answered well but: 58–65% of its claims had no citation, 31–35% of quoted passages were not verbatim, it added cases from general knowledge (or-06), and it opened with a bare Yes/No on broad questions. Citations are also hard to read (`§u59`) and links don't land on the quoted text.

## What to build
1. **Text fragments.** Every `hudoc_url` the server returns (every tool, every place it appears) gets `:~:text=<first 6–8 words of that result's verbatim quote>` appended after HUDOC's existing `#{...}` part, with no extra `#`. Percent-encode per the text-fragment spec: spaces as `%20`, and also encode `-`, `&` and `,` (plus anything `encodeURIComponent`-style would encode; unreserved letters/digits stay). Use the exact quote text the result returns (not a normalised one). Where a result has no quote, leave the URL as is and document that. Unit-test the encoding, including quotes containing `-`, `&`, `,`, quotes, accents and § signs. Ensure the URL stays well-formed and within the contract's length limit (adjust the limit in the contract only if needed and say so).
2. **Readable labels.** Add a display field `para_label` to every result item that carries a paragraph: `"§79"` for numbered paragraphs; for unnumbered ones (legal summary, operative provisions, etc.) `"<Section>, para <n>"` e.g. `"Law, para 2"`, `n` counted within that section in document order. Read how paragraph IDs and section labels look in the data (`§79`, `§u59`, `§op1`, …) before choosing; document the rules in `docs/learn/mcp.md`. The `cite` string uses it: `[Harkins v. the United Kingdom, Legal summary, Law, para 2]`, `[Chahal v. the United Kingdom, Judgment, §79]`. `paragraph_id` and everything keyed on it are **unchanged**. Update the contract (zod → JSON Schema), regenerate fixtures, update tests on both sides (`pnpm check` runs TS and Python). The eval harness maps `cite` strings back to paragraph ids using what the tools returned, so keep `cite` strings unique per paragraph within a result set (if two paragraphs would get the same label, disambiguate and test it).
3. **Server instructions and tool descriptions** (`INSTRUCTIONS`, `TOOL_SPECS` in `py/echr_mcp/server.py`): short, explicit, in this order of importance:
   - Every factual sentence ends with a `cite` string copied from a tool result, or it does not go in.
   - Quote only text copied from tool results; call `check_quote` before any quoted phrase.
   - Use only cases returned by the tools. If nothing relevant comes back, say so and state the corpus limits (from `corpus_info`). Never add cases from general knowledge.
   - Open with one sentence that answers the question, even for broad questions; then grouped evidence; about 8–10 claims maximum.
   - No bare Yes/No unless a cited paragraph states the general rule; otherwise lead with the holding's reach ("Only where…", "Not as a general rule…").
   - Use `count_cases` for any how-many question.
   Keep the existing neutrality and legal-summary lines if they fit; total instructions short (aim ≲ 250 words). Tool descriptions: say what the result's `cite`, `quote`, `hudoc_url` are for.
