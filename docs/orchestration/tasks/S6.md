## Build

1. **Question set `data/eval/questions.jsonl`:** one `EvalItem` per line, **60–80 items, all `status: "draft"`** for Dan to review.
   - **Mix:**
     - ≥ 40 `explain` questions;
     - ≥ 8 `stat` (counting) questions with expected counts derived from `data/snapshot/manifest.json` and the grounds oracle;
     - ≥ 8 `neutrality` questions: contested topics such as deportation of criminals, prisoner voting (Hirst), extraterritorial jurisdiction (Al-Skeini), and "should the UK leave?".
   - **Sources:**
     - seed from the 15 legal summaries, each of which points to key judgment paragraphs;
     - hand-write the rest from the judgments and decisions;
     - include the three demo questions verbatim.
   - **Expected paragraph IDs:** every item has them. A test checks every expected ID exists in the parsed snapshot: use `rag.parse` once merged, and a skip-if-missing fallback before that.
   - **Tags:** article, theme, difficulty.
   - **Your own effort only:** write the questions yourself; no API calls are needed for drafting.
2. **Metrics** (`py/rag/eval/metrics.py`, unit-tested with hand-computed examples):
   - **recall@5 and recall@10:** a hit counts if any of its `paragraph_ids` is expected.
   - **MRR.**
   - **faithfulness:** judge = `judge_model()` (Sonnet) via `rag.answer.llm.complete` with purpose `judge`. Scored 0–1 with a short rubric: is every claim supported by its cited paragraphs?
   - **citation accuracy:** the share of citations whose paragraph supports its claim, by judge. You may reuse S4's verification status, but say which you chose.
   - **neutrality pass rate:** judge rubric on `neutrality` items: presents sourced positions on each side, and gives no opinion on UK membership or policy.
   - **stat accuracy:** the count matches the expected value.
3. **Runner** `python -m rag.eval --source snapshot [--quick] [--no-judge] [--max-cost 3.00]` (that's `pnpm eval:snapshot`):
   - **Retrieval metrics** for **every chunking strategy × search mode** (3 × 4 = 12 configs). These are local and cost $0.
   - **Answer-level metrics** for the default config (`hybrid_rerank` + `recursive`), plus one comparison config of your choice.
   - **Cost guard:** print an estimated cost before any judge calls and abort if it's above `--max-cost`.
   - Store an `EvalRun` per config in `eval_runs`.
   - Write `docs/eval-results.md`: a table with one row per config, metrics, cost and time, and a plain-English "what this shows" paragraph.
   - Replace the README marker section with a compact version.
   - `--quick` = 10 questions, retrieval only, for smoke tests.

## Common rules for every Gate 1 task

### Project context
`echr-lookup` is a learning and portfolio RAG (Retrieval-Augmented Generation) system over the UK's case law at the European Court of Human Rights (HUDOC), plus the Convention and the Human Rights Act 1998. It answers questions neutrally and never takes a side on UK membership. Every claim cites a paragraph ID like `001-57619§88`, and every citation is verified. Counting questions are answered with SQL over metadata. Dan (the owner) is technical but new to RAG.

Pipeline: ingest (S1) → parse + chunk (S2) → embed + index (S3) → search (S3) → answer, citation check and stats SQL (S4) → FastAPI (S5) → web UI (Gate 2). Eval is S6; the screenshot helper is C1.

The demo path that must work in snapshot mode (local, offline except Anthropic calls) is:
1. `/ask` "Does the Convention stop the UK deporting criminals?" → a balanced answer, every sentence cited (Article 3 and Article 8 deportation cases), including at least one case where deportation was allowed. Clicking a citation opens the paragraph highlighted on `/case/<id>`.
2. `/ask` "How has Article 8 been applied in UK immigration cases?" → a cited summary across several cases.
3. `/ask` "How many UK deportation complaints in the corpus were declared inadmissible, and the most common reasons?" → the stats route: count, top reasons, the SQL used, and the cases listed.
4. `/lab`: the step-1 query side by side as BM25, vector, fused and reranked, with scores and chunking strategy.
5. `/stats`: corpus counts, the last ingest run with timings, running cost from `cost_log`, and the eval results table.

Budgets: answer < 15 s, search < 3 s.
