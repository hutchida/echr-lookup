# Task S3: Index + search

- **Model:** `github-copilot/claude-sonnet-5.5` (opencode)
- **Database:** `echr_s3`
- **Merge position:** 2nd
- **Depends on:** S2 (`rag.parse`) for real chunks. Until it merges, see "Data for development" below.

## Goal
Store documents, paragraphs and chunks in Postgres with **both** a BM25 index (pg_search) and vector embeddings (pgvector). Then implement search in four modes: `bm25`, `vector`, `hybrid` (Reciprocal Rank Fusion) and `hybrid_rerank` (cross-encoder), with metadata filters and **per-method scores** so the Lab page can show what each step contributes.

Everything else.

## Build (signatures and tables fixed by `docs/interfaces.md` §2–3)

1. **Migrations.** `infra/migrations/0001_*.sql …` create exactly the tables and columns in interfaces §3, the BM25 index on `chunks`, and an HNSW `vector_cosine_ops` index on `chunks.embedding`. `migrate()` is idempotent (`schema_migrations`). `reset()` drops the app tables and re-migrates. Use regular tables, never TEMP tables (D-001).
2. **Embedder.**
   - `get_embedder()` returns a sentence-transformers `BAAI/bge-small-en-v1.5`: 384 dimensions, L2-normalised, CPU, batch size 32, loaded once per process. It also provides `count_tokens` using the model's tokenizer.
   - `"fake"` gives deterministic hash-based vectors (dimension 384, no ML imports).
   - Keep it behind the `Embedder` protocol, so a paid embedder could be added later. **Never call a paid embedder.**
3. **Writes:** `upsert_document`, `replace_chunks`, `stored_hashes`, `record_ingest_run`.
4. **Cost logging:** `log_cost` / `price_usd` read `config/model-prices.json`. Local models cost $0 but still get a row. Apply Haiku 5.5's > 100K-token tier per request.
5. **`search(conn, request)`**:
   - **bm25:** top N=50 by `paradedb.score`.
   - **vector:** top N=50 by cosine.
   - **hybrid:** RRF with k=60 over both lists.
   - **hybrid_rerank:** cross-encoder `BAAI/bge-reranker-base` over the top 30 fused results. `"fake"` reranker for tests. Respect `rag.config.rerank_enabled()`.
   - **Filters:** `article`, `doc_types`, `outcomes`, `date_from` / `date_to`. Join to `documents`, and apply the filters **inside** both retrievers, not after.
   - Filter by `chunking` strategy.
   - Fill **every** score/rank field for the methods that ran (null otherwise), plus `timings_ms`. Cap at 50 hits.
   - `paragraph_ids` on each hit is the cited subset of `chunk.paragraph_ids`, as described in the contract. If unsure, use all of them.
   - Log the query embedding and rerank via `log_cost`.
6. **CLI** `python -m rag.search …` (that's `pnpm search`): a readable table of rank, case, paragraph IDs, each method's score/rank and a text snippet.

## Common rules for every Gate 1 task

### Project context
`echr-lookup` is a learning and portfolio RAG (Retrieval-Augmented Generation) system over the UK's case law at the European Court of Human Rights (HUDOC), plus the Convention and the Human Rights Act 1998. It answers questions neutrally and never takes a side on UK membership. Every claim cites a paragraph ID like `001-57619§88`, and every citation is verified. Counting questions are answered with SQL over metadata. Dan (the owner) is technical but new to RAG.

Pipeline: ingest (S1) → parse + chunk (S2) → embed + index (S3) → search (S3) → answer, citation check and stats SQL (S4) → FastAPI (S5) → web UI (Gate 2). Eval is S6; the screenshot helper is C1.

The demo path that must work in snapshot mode (local, offline except Anthropic calls) is:
1. `/ask` "Does the Convention stop the UK deporting criminals?" → a balanced answer, every sentence cited (Article 3 and Article 8 deportation cases), including at least one case where deportation was allowed. Clicking a citation opens the paragraph highlighted on `/case/<id>`.
2. `/ask` "How has Article 8 been applied in UK immigration cases?" → a cited summary across several cases.
3. `/ask` "How many UK deportation complaints in the corpus were declared inadmissible, and the most common reasons?" → the stats route: count, top reasons, the SQL used, and the cases listed.
4. `/lab`: the step-1 query side by side as BM25, vector, fused and reranked, with scores and chunking strategy.
5. `/stats`: corpus counts, the last ingest run with timings, running cost from `cost_log`, and the eval results table.

Budgets: answer < 15 s, search < 3 s.
