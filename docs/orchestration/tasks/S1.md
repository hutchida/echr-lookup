## Goal
`pnpm ingest:snapshot` and `pnpm ingest:full` load documents into the database through parse → chunk (all 3 strategies) → embed → index. Runs are **resumable** and **incremental**: unchanged documents are skipped by content hash, so new material can be added any time. Each run records an `IngestRun` with per-stage timings and shows progress with an ETA.

## Owned paths
- `py/rag/ingest/**` (with tests)
- `scripts/ingest/**` (optional helpers)
- `docs/learn/S1.md`

## Must not touch
Everything else, including root `package.json`: the scripts already call `python -m rag.ingest --source snapshot|full`.

## Build (`run_ingest` and CLI per `docs/interfaces.md` §2)

1. **Snapshot mode** (offline, the demo default):
   - read `data/snapshot/manifest.json` (`ManifestEntry` list) and each stored file;
   - verify the sha256;
   - skip documents whose sha256 equals `stored_hashes()` (count `unchanged_skipped`);
   - otherwise parse, chunk with each of the 3 strategies (passing `embedder.count_tokens`), embed (batch 32), `replace_chunks`, `upsert_document`.
   - Include the Convention and HRA files.
   - `--reset` calls `rag.index.reset()` first, giving "from empty".
   - `--limit N`.
   - `record_ingest_run` at the end with stage seconds (download, parse, chunk, embed, index; download ≈ file reads in snapshot mode) and counts (seen, new, changed, unchanged_skipped, failed).
   - A failure on one document is logged, counted and does not abort the run.
2. **Progress output:** one line per document, plus a running ETA computed from the measured per-document time, and a final summary table.
3. **Full mode.** HUDOC sits behind a **Cloudflare managed challenge**: plain HTTP clients get 403. **Dan approved this approach:** HUDOC requests are same-origin `fetch()` calls inside **Orca's built-in browser tab** via `orca eval`, as G0b did (read `scripts/g0b/hudoc.py`, and port its ideas, not its code paths).
   - Find a tab on `https://hudoc.echr.coe.int` with `orca tab list --json`, and target it by `--page <id>`. If there's none, open one with `orca tab create --url https://hudoc.echr.coe.int/eng`.
   - **Never attempt to solve or bypass the challenge.** If a response is a challenge page or a 403, stop cleanly: save resumable state and print a plain instruction for a human to open the HUDOC tab in Orca and complete any check, then re-run.
   - **≤ 1 request/second enforced in code**: a cross-process file lock plus a timestamp, as G0b did. Add a configurable hard cap and a JSONL request log in `data/full/`.
   - **Listing:** use the exact UK English queries from `docs/hudoc-measurement.md` (judgments, Court and Commission decisions, communicated cases, legal summaries, Commission reports; not Committee of Ministers resolutions), with `length=500` pages.
   - **Download:** HTML bodies (`/app/conversion/docx/html/body?…`) into `data/full/hudoc/<itemid>.html`. Write `data/full/manifest.json` as `ManifestEntry` records built from listing metadata (normalise outcome, chamber and so on as G0b's manifest does).
   - **Resumable:** skip files already downloaded. **Incremental:** content-hash skip as in snapshot mode.
   - **Non-HUDOC sources** (legislation.gov.uk, echr.coe.int) use `httpx` with User-Agent `echr-lookup/0.1 (+https://github.com/hutchida/echr-lookup)`.
   - **Do NOT run a full ingest.** During development you may hit HUDOC with `--limit 5`, at most twice (**≤ 30 HUDOC requests for the whole task**). The orchestrator runs the one real full ingest at the Gate 1 check.
4. **Unit tests** (offline, with a fake transport and a fake clock): rate limiter spacing, resume after interruption, incremental skip, challenge detection → clean stop, and `IngestRun` validation against the contract.

## Common rules for every Gate 1 task

### Project context
`echr-lookup` is a learning and portfolio RAG (Retrieval-Augmented Generation) system over the UK's case law at the European Court of Human Rights (HUDOC), plus the Convention and the Human Rights Act 1998. It answers questions neutrally and never takes a side on UK membership. Every claim cites a paragraph ID like `001-57619§88`, and every citation is verified. Counting questions are answered with SQL over metadata. Dan (the owner) is technical but new to RAG.

Pipeline: ingest (S1) → parse + chunk (S2) → embed + index (S3) → search (S3) → answer, citation check and stats SQL (S4) → FastAPI (S5) → web UI (Gate 2). Eval is S6; the screenshot helper is C1.

The demo path that must work in snapshot mode (local, offline except Anthropic calls) is:
1. `/ask` "Does the Convention stop the UK deporting criminals?" → a balanced answer, every sentence cited (Article 3 and Article 8 deportation cases), including at least one case where deportation was allowed. Clicking a citation opens the paragraph highlighted on `/case/<id>`.
2. `/ask` "How has Article 8 been applied in UK immigration cases?" → a cited summary across several cases.
3. `/ask` "How many UK deportation complaints in the corpus were declared inadmissible, and the most common reasons?" → the stats route: count, top reasons, the SQL used, and the cases listed.
4. `/lab`: the step-1 query side by side as BM25, vector, fused and reranked, with scores and chunking strategy.
5. `/stats`: corpus counts, the last ingest run with timings, running cost from `cost_log`, and the eval results table.

Budgets: answer < 15 s, search < 3 s.
