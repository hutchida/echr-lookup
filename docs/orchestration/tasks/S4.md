## Build (signatures fixed by `docs/interfaces.md` §2 `rag.answer`)

1. **`rag.answer.llm.complete`.** This is the only Anthropic call site in the app.
   - Build the client explicitly: `anthropic.Anthropic(api_key=rag.config.anthropic_api_key(), base_url=rag.config.anthropic_base_url())`.
   - Retry with tenacity on 429/5xx. Use prompt caching for long static system prompts where it helps.
   - Log every call via `rag.index.log_cost` (tokens in, out and cached; latency).
   - `LLM_MODE=fake` returns deterministic canned outputs keyed by purpose, so the whole pipeline runs offline in tests.
2. **Router `route()`.** A cheap heuristic first (counting words like "how many", "number of", "most common", "percentage"), then `router_model()` (Haiku) for anything ambiguous. It returns `rag` or `stats`. Test it on a small labelled list that includes the three demo questions.
3. **RAG path.**
   - **Retrieve** with `rag.search.search`. Default mode `hybrid_rerank`, chunking `recursive`, k=12; `AnswerRequest.options` can override these.
   - **Context:** build it from the cited paragraphs with their IDs and case names.
   - **Neutral system prompt:**
     - answer only from the sources;
     - present the strongest sourced points on each side of contested issues;
     - **never** give an opinion on UK membership of the Convention, or on whether a law is good or bad;
     - say plainly "the sources provided don't answer this" when that's true (set `refused_or_not_in_sources`).
   - **Generation** with `answer_model()` (Sonnet) as structured JSON. Each claim gets `citation_ids` that must be paragraph IDs from the context. Reject or repair any ID not in the context.
   - **`answer_text`:** sentences with inline markers like `[Soering v UK §88]`.
   - **`citations[]`:** a verbatim quote (trimmed) and `link_target = "/case/<doc_id>#p<ref>"`, where `<ref>` is the part after `§` (e.g. `/case/001-57619#p88`, `#pop3`, `#pu2`). Gate 2's case viewer anchors paragraphs with exactly these `id`s.
4. **Per-claim verification.**
   - For each claim, `verify_model()` (Haiku) reads only the cited paragraph(s) and returns `supported` / `unsupported` / `unverified` with a short reason. Run claims **in parallel** (thread pool) to keep latency down.
   - Unsupported claims are **removed from `answer_text`**, but stay in `claims[]` with their status, so the UI can show what was dropped. If verification itself fails, the claim stays as `unverified`.
5. **Stats path `run_stats()`.**
   - The SQL runs over the tables in interfaces §3, in a **read-only transaction** with `statement_timeout` 3 s. Use only SELECTs on whitelisted tables.
   - Prefer **parameterised templates**, with Haiku extracting the parameters: article, doc type, outcome, date range, topic keywords. Free-form LLM SQL is allowed only if you validate it as a single read-only SELECT on the whitelist.
   - Return `StatsQueryResult`: the SQL text actually run, the rows, the count, matching cases as citations, and a plain explanation.
   - **Demo Q3 needs "deportation complaints".** Metadata has no topic field, so identify the topic transparently, e.g. by text match on `paragraphs.text` (deport / expel / expulsion / extradit / removal) and/or the articles. Show it in the SQL, and explain the definition in the answer.
   - "Most common reasons" come from `documents.inadmissibility_grounds`, filled by S2 from the decision text; unnest and count them.
6. **`answer()`** assembles an `Answer`:
   - route, claims, citations, stats (or null);
   - `steps[]` with per-step tokens, cost and latency;
   - `total_cost_usd`, `models_used`.
   - It must stay **< 50 KB**: enforce caps by trimming quotes and limiting claims.
7. **CLI** `python -m rag.answer "<question>"` (`pnpm ask`) prints the answer, citations with verification badges, the route, the SQL (stats) and the cost.

## Acceptance (in addition to the common rules)
- **Offline (fake LLM) tests:** routing; claim/citation assembly; unknown citation IDs rejected; unsupported claims removed from the text; the stats SQL is read-only (a write attempt fails); `Answer` and `StatsQueryResult` validate against the contract; payload < 50 KB.
- **Live checks (`@pytest.mark.live`, run locally with `RUN_LIVE=1`; never in CI):** prompt sanity on handcrafted context built from real snapshot paragraphs (e.g. Soering §88, an Article 8 no-violation deportation case). Results: all claims cited, the neutral framing holds, and an off-topic question ("Should the UK leave the ECHR?") is answered with sourced positions and no opinion.

## Common rules for every Gate 1 task

### Project context
`echr-lookup` is a learning and portfolio RAG (Retrieval-Augmented Generation) system over the UK's case law at the European Court of Human Rights (HUDOC), plus the Convention and the Human Rights Act 1998. It answers questions neutrally and never takes a side on UK membership. Every claim cites a paragraph ID like `001-57619§88`, and every citation is verified. Counting questions are answered with SQL over metadata. Dan (the owner) is technical but new to RAG.

Pipeline: ingest (S1) → parse + chunk (S2) → embed + index (S3) → search (S3) → answer, citation check and stats SQL (S4) → FastAPI (S5) → web UI (Gate 2). Eval is S6; the screenshot helper is C1.

The demo path that must work in snapshot mode (local, offline except Anthropic calls) is:
1. `/ask` "Does the Convention stop the UK deporting criminals?" → a balanced answer, every sentence cited (Article 3 and Article 8 deportation cases), including at least one case where deportation was allowed. Clicking a citation opens the paragraph highlighted on `/case/<id>`.
2. `/ask` "How has Article 8 been applied in UK immigration cases?" → a cited summary across several cases.
3. `/ask` "How many UK deportation complaints in the corpus were declared inadmissible, and the most common reasons?" → the stats route: count, top reasons, the SQL used, and the cases listed.
4. `/lab`: the step-1 query side by side as BM25, vector, fused and reranked, with scores and chunking strategy.
5. `/stats`: corpus counts, the last ingest run with timings, running cost from `cost_log`, and the eval results table.

Budgets: answer < 15 s, search < 3 s.
